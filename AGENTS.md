# Architecture decisions

- MCP server is disabled (no /mcp, /.mcp/*, /.well-known/oauth-protected-resource, /.lovable/oauth/consent routes; no @lovable.dev/mcp-js). Why: not needed now; rebuild later from the archived copy (Files → mcp-archive), reusing `src/lib/cities.ts` and `src/lib/contact-info.ts`.
- Design tokens are scoped under `.theme-public` / `.theme-portal` in `src/styles.css`; new UI uses `src/components/ds/*` + `src/components/brand/*`. Why: keeps the preserved training screens on neutral tokens and lets a future admin theme editor override one central token set.
- Public pages use uppercase H1/H2 headings; one-column section heads center as a complete group, while two-column heads explicitly opt into left alignment. Why: keeps hierarchy and alignment consistent site-wide.
- Transportation accounts use `workspaces` + `workspace_members` (owner/admin/member) with `user_profiles`; setup runs atomically in `complete_account_setup()` and post-sign-in routing comes from server fn `getAccessState` (src/lib/access.functions.ts). Why: server-verified access, training-only users need no workspace, platform admin stays in `user_roles`.
- Location, service and resource pages are data-driven (`src/lib/coverage.ts`, `src/lib/services-content.ts`, `src/lib/resources-content.ts`); coverage regions must mirror the map regions in FloridaMap.tsx, and county pages exist only where a city page exists. Why: one source for sitemaps/links and no thin duplicate pages.
- All transportation/delivery requests go through `submitRideRequest` / `submitDeliveryRequest` (schemas in `src/lib/request-schemas.ts`, requester + workspace resolution in `src/lib/requests/request-service.server.ts`); `ride_requests` has no anon/authenticated INSERT and `trip_kind` separates passenger vs medical_delivery. Why: one validated, server-authorized entry point; account access derived server-side only.
- Request emails carry only the short request number, status/category and safe contact text. Why: request details are viewable only after authorized sign-in.
- Portal/admin request reads go through `src/lib/portal-requests.functions.ts` as the signed-in user so row-level rules decide visibility; workspace-wide viewing needs owner/admin or `workspace_members.can_view_workspace_requests` (contractors never), and `trips` has no role-title-only access. Why: dispatcher/zone titles must never grant statewide data.
- One shared request form (`src/components/requests/RequestForm.tsx`) serves /book and /portal/requests/new; Medical Delivery rows are never promoted into `trips`. Why: one validated path, deliveries get their own workflow later.
- Permanent MFN IDs (`MFN-P-`/`MFN-A-`/`MFN-R-`) are assigned and frozen by database triggers on user_profiles/workspaces/ride_requests; they are display IDs only, never used for authorization. Why: non-PII, immutable references while UUIDs + RLS stay the security authority.
- The single Master Admin lives in `platform_master_admin`; only it may grant/remove the admin role (RLS + trigger + server checks in admin-users.functions.ts). Why: regular admins must never alter or demote the owner.
- `workspaces.organization_type` is a business label only (src/lib/account-types.ts); portal kind (provider vs customer) comes from `account_type` via getAccessState. Why: classification must never grant permissions.
- Restored old portal panels live in src/components/dashboard|admin and are restyled through the shadcn-token bridge in `.theme-portal` (styles.css); the open-request claiming panel and direct CSV bulk insert are intentionally not restored. Why: reuse old behavior without weakening the Pass 3B access model.
- Full admin power belongs only to the Master Admin: `has_role(…,'admin')` is true only for the master; regular admins hold the label (`holds_admin_label`) and act only through `admin_can(section, level)` + `admin_can_account(workspace)` (tables admin_permissions / admin_permission_scopes, master-only writes, audited). Why: an admin title alone must never grant access.
- Every ride_requests write goes through `insertPassengerRequest` / `insertDeliveryRequest` in request-service.server.ts (public, portal, admin-on-behalf, CSV import). Test-account rows are flagged `is_test` by trigger and never promoted to trips or emailed. Why: one validated path and no test data in live operations.
- Provider Network listings live in `provider_network_profiles` and are read only through RPC `list_network_providers` (verified + active + visible + non-test); `workspaces.provider_verified` is platform-set only; one shared `src/components/network/ProviderDirectory.tsx` serves Network, Find Providers and Saved Providers. Why: one safe public-field directory, no self-verification.
- Master-Admin portal previews (`admin_.preview.$kind.tsx`) use the real PortalShell + shared nav (`src/components/portal/portal-nav.ts`) with synthetic data and no server calls. Why: no impersonation or real data in previews.
- Business-to-business workspace messaging (`workspace_conversations`/`workspace_messages`) writes go only through `src/lib/workspace-messages.functions.ts` after independently re-checking `can_access_workspace_messages` server-side; both tables have SELECT-only RLS (service-role does inserts/updates) and there are no notifications or emails for new messages. Why: owner/admin/flagged-member access must be verified on every write, not assumed from the client.
- Smart Notes live in `workspace_notes` (private to creator within an active workspace via RLS; creator/workspace MFN IDs stamped and frozen by trigger); `visibility` only allows 'private' until team sharing is designed. Why: notes must never cross workspaces or live in the browser.
- Portal features for future public display are tracked in `src/lib/feature-catalog.ts`; only entries with `publicApproved: true` and status complete may be shown publicly. Why: unfinished tools must never appear on the homepage by default.
- Provider Trips has addressed network offers plus legacy referrals, Reservations, own secure Drafts and History; network acceptance writes association columns on the existing trips record through locked database RPCs. Why: preserves original sources without exposing a statewide pool or duplicating trips.
- Vehicles/drivers/contacts/payers use workspace RLS with explicit record_permissions and record-specific shares; creator/MFN audit identity is immutable and workspace stamping requires one verified membership. Why: business ownership must not depend on the person editing or browser-supplied workspace IDs.
- Controlled distribution actions live in authenticated trip-network.functions.ts wrappers and database RPCs; prospective-provider reads project safe general fields, and negotiation/event history is append-only. Why: permissions and atomic selection remain authoritative even when UI is bypassed.
- Draft resume passes only a UUID in route search and restores owner-scoped database payloads into the shared request form. Why: personal/trip information must not be persisted in browser storage or URLs.
- Portal request/trip viewing uses one shared RLS-scoped overlay provider; prospective offers use the same overlay frame with only safe offer fields. Why: entry-point UI cannot broaden private record access.
- Shared request field semantics live in request-detail-fields; linked booking data merges only through the caller's RLS-scoped source read. Why: missing, inapplicable and unauthorized fields stay distinct without elevating access.
- Provider trip sharing validates payment-responsibility acknowledgement before invoking distribution creation. Why: showing a warning alone must not allow unacknowledged sharing.
- User removal uses credential-destroying Auth soft deletion only for dependency-free Master-Admin removals, otherwise bans login and retains profile/membership tombstones; database preflight scans UUID relationships. Why: legacy Auth foreign keys must never cascade-delete history.
