# Architecture decisions
- Sandbox review extends existing commerce/events; no Stripe calls or timer-only release. Why: preparation never proves funding.

- App MCP (src/lib/mcp) is OAuth-only with public-info tools; consent returns via login/create-account `redirect`. Why: no private data to ChatGPT.
- Managed emails retain signed deduped history; legacy Maps/driver queues stay separate. Schedule preparation uses RLS and minimal account_security_audit confirmation, never sends. Why: preview never sends.
- Design tokens live under .theme-public/.theme-portal; new UI uses ds/brand components. Why: neutral training and central overrides remain intact.
- Public pages use uppercase H1/H2; one-column section heads center as a group, two-column heads opt into left alignment. Why: consistent hierarchy.
- Transportation uses workspaces/members/profiles, atomic `complete_account_setup()` and server-verified `getAccessState`; platform roles stay in `user_roles`. Sidebar/guards share `isPortalPathBlocked`; CSV matches existing single active eligible customer membership. Why: no broader permissions; learners need no workspace.
- Coverage/services/resources use shared content modules; regions mirror FloridaMap and counties require cities. Why: consistent links without thin duplicate pages.
- All request writes (public, portal, admin-on-behalf, CSV) use insertPassengerRequest/insertDeliveryRequest in request-service.server.ts and shared schemas; client INSERT is revoked, workspace resolution server-side, delivery separate. Triggers validate/stamp patient targets and flag test rows; tests never become trips or emails. Network exposes general fields until accepted follow-up, never books/charges. Request emails carry only the short request number, status/category and safe contact text. Why: one boundary, no broadcast or live test data.
- Portal/admin request reads go through `src/lib/portal-requests.functions.ts` as the signed-in user so row-level rules decide visibility; workspace-wide viewing needs owner/admin or `can_view_workspace_requests` (contractors never); `trips` has no role-title-only access. Why: titles never grant statewide data.
- RequestForm serves /book, portal and admin customer intake; delivery never becomes a trip. Lifecycle moves only via transition_request_lifecycle (append-only history); auto-distribution waits on platform_launch_flags (missing=off). Why: no skipping; shared live DB.
- Permanent MFN IDs (`MFN-P-`/`MFN-A-`/`MFN-R-`) are assigned and frozen by database triggers on user_profiles/workspaces/ride_requests; they are display IDs only, never used for authorization. Why: non-PII, immutable references while UUIDs + RLS stay the security authority.
- The single Master Admin lives in `platform_master_admin`; only it may grant/remove the admin role (RLS + trigger + server checks in admin-users.functions.ts). Why: admins never demote the owner.
- `workspaces.organization_type` is a business label only (src/lib/account-types.ts); portal kind (provider vs customer) comes from `account_type` via getAccessState. Why: labels never grant permissions.
- Restored dashboard/admin panels use the portal token bridge; Fleet & Drivers reuses FleetPanel with legacy section redirects, Earnings & Payments reuses owner-scoped tools. Open claiming and direct CSV inserts stay off. Why: preserve actions and permissions.
- Full admin power belongs only to the Master Admin: `has_role(…,'admin')` is true only for the master; regular admins hold the label (`holds_admin_label`) and act only through `admin_can(section, level)` + `admin_can_account(workspace)` (tables admin_permissions / admin_permission_scopes, master-only writes, audited). Why: an admin title alone must never grant access.
- ProviderDirectory shares verified/active/visible/non-test RPC reads; provider_verified stays platform-set. Opted-in public proximity centers stay separate from private verified offer bases. Why: no self-verification or home-location exposure.
- Master-Admin portal previews (`admin_.preview.$kind.tsx`) use the real PortalShell with fixtures from portal/demo-fixtures (one flag), separate cache, no server calls. Why: no impersonation or real data in previews or live reads.
- Workspace messaging writes recheck can_access_workspace_messages server-side; referral messaging resolves parties from trip_distributions server-side; tables have SELECT-only RLS and service writes, no notifications/emails. Why: every write verifies owner/admin/flagged-member access.
- Smart Notes live in `workspace_notes`, private to creator within an active workspace via RLS; creator/workspace MFN IDs frozen by trigger; `visibility` allows only 'private' until team sharing is designed. Why: notes never cross workspaces or live in the browser.
- Portal features for future public display are tracked in `src/lib/feature-catalog.ts`; only `publicApproved: true` complete entries may be shown publicly. Why: unfinished tools stay off the homepage.
- Provider Trips holds owned operations, accepted referrals, Reservations, Drafts and History; ProviderNetworkPage holds offers, proposed amounts and sent activity in live and preview. Acceptance updates existing trips via locked RPCs. Why: separate network negotiation from owned trips without duplication or an open pool.
- Vehicles/drivers/contacts/payers use workspace RLS, record_permissions and shares; creator/MFN identity immutable. Fleet status changes only via set_fleet_resource_status (append-only, inactive blocks new assignments, never delete); provider API keys are hash-only, read scopes. Why: ownership never trusts browser IDs.
- Controlled distribution actions live in authenticated trip-network.functions.ts wrappers and database RPCs; prospective-provider reads project safe general fields, and negotiation/event history is append-only. Why: permissions and atomic selection remain authoritative even when UI is bypassed.
- Draft resume uses UUID URLs/owner-scoped payloads; shared request/trip overlays enforce RLS and show safe fields only. Why: no browser persistence, auto-submit or broader access.
- User removal uses credential-destroying Auth soft deletion only for dependency-free Master-Admin removals, otherwise bans login and keeps profile/membership tombstones; preflight scans UUID relationships. Why: legacy Auth foreign keys must never cascade-delete history.
- Training uses server-only keys, user-scoped records and verified in-memory checkout. Why: one identity.
- Shared personal settings use strict owner RPC/audit; provider tabs reuse tools, legacy credentials/integrations remain owner-scoped, exports use owned/accepted RLS trip rows. Why: never widen permissions.
- Secure email changes require server AMR/password reauthentication; Auth lifecycle triggers audit requested/confirmed/canceled and provider code failures audit failed/expired. Why: client events never prove confirmation or store secrets.
- Network settlement: immutable `network_settlements` per referral (DB trigger); locked `network_payment_attempts` priced by DB fee policy; only webhooks mark Paid/Held; attempts lock fee terms, variance is record-only; Connect events use own route/secret; hold via `network_receiver_hold_tier`. Why: clients never set money or holds.
- Automatic badges use one database evaluator, event triggers and a prepared SQL-only lifecycle; live membership/Connect linkage, protected attested documents and scoped safe summaries required. Legacy NULL labels stay separate. Why: browser fields, checkout and uploads alone never prove verification.
- Contacts and Payers share portal.contacts.tsx tabs; /portal/payers redirects there; contacts link via provider_contacts.payer_id. Why: one record, no duplication.
- Uploads (CSV/XLSX/PDF) only create owner drafts via uploads.functions.ts; originals stay 7 days in private `import-uploads`. Exports use src/lib/table-export.ts. Why: uploads never submit; one exporter.
- Provider API (/api/public/provider/v1/*) is read-only, Bearer-only, hash-matched, rate-limited, workspace-scoped; driver schedule sends stop before any write while their flag is off. Why: keys never widen access.
- Launch Readiness (/admin/launch) is Master-Admin-only, read-only, statuses only (flags missing=off, secret presence never values). Why: no activation path.
- Provider Settings uses six shared groups; additive service roles never replace primary subtype. Fleet/preferred-driver gates are workspace-scoped and accepted alerts reuse immutable notification evidence. Why: no wider permissions, duplicate relationships or delivery.
- Setup acknowledgment is separate from purchase clickwrap; completed progress is retained and existing identity classification never changes on resume. Why: onboarding cannot retroactively alter consent, access or verification.
- Existing-account connection requests reuse invitation records with server-resolved recipients and no delivery; usual-provider changes require active bilateral connections. Exact contact lookup stays disabled until owner-approved rate limiting. Why: no enumeration or implied trip access.
- Patient/Facility account verification uses server-derived profile evidence and existing security audit, not provider badges or authorization; evidence triggers and read-time checks invalidate stale display without backfills. Why: profile completeness must never grant access.
- New Trip uses basic allowlisted authorized defaults and immutable patient/contact/payer references with database guards; inline CRM forms reuse the existing models and payment-method mutations stay disabled. Why: no PII browser persistence, cross-workspace billing or automatic Network sharing.
- New Trip estimate refresh is read-only through the existing server calculator; quote attachment compares the full trip and reviewed pricing inputs, and patient detail display uses a second safe allowlist. Why: stale prices cannot silently attach and worksheet presentation never exposes internal fields.
- Large neutral canvases explicitly opt into one CSS texture token; children never inherit background images and accessibility/print modes suppress it. Why: shared intensity cannot texture controls, colored statuses or private Notes surfaces.
